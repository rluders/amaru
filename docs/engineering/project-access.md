# Compact Project access boundary

[ADR-0062](../architecture/adr/0062-project-bound-public-operations-and-secret-resolution.md) is accepted following owner approval in [PR #330](https://github.com/rluders/amaru/pull/330). `coordinator.ProjectAccess` implements the first #191 application slice around existing Execution operations. It does not implement a product HTTP server or complete [#191](https://github.com/rluders/amaru/issues/191).

Construct `NewProjectAccess` with the existing coordinator, the Instance's attached Project store and `localauth.Auth.Principal`. Every call rechecks authentication and attached Project identity. Compact composition has one configured Organization; its local administrator has owner access to those Projects. No membership database or multi-Organization authorization is implemented. The authentication callback is a trusted composition dependency, never a principal decoded from a request body or headers. A custom callback must enforce current authorization on every call.

`Auth.Principal` accepts only context established by that Auth instance's guarded downstream dispatch. Credential-free health/root requests and another Instance's context confer no identity. It refuses cancelled requests, logged-out/expired browser sessions and shutdown native contexts. Identity is the Instance-local `local-administrator`; session IDs and bearer values never become domain actor IDs. Origin/CSRF checks still precede authenticated dispatch.

`ProjectAccess` uses the coordinator's own authoritative store, preserving the trusted internal APIs for scheduling and recovery. It refuses invalid/unattached Project selectors before resource lookup. A foreign or missing Execution/Approval returns exactly `domain.ErrNotFound` with no returned child records, replay outcome or cursor. Approval ownership checks both its Project and its gating Execution. Ownership is checked before calling command replay or Evidence's context/artifact/audit readers. Existing stores already preserve immutable Execution Project identity; this slice changes no persisted storage contract, migration or transaction semantics. A read-only `ports.EvidenceReader` keeps the coordinator dependent only on domain/ports; trusted composition supplies the existing Evidence reader.

Manual Submit derives Project, principal and trigger from the trusted boundary. Cancel derives the human Actor and ActorID; Approval decisions derive their principal. Existing coordinator Policy, Approval, version checks, atomic writes and `(command name, key)` command namespace remain in force. Same-key requests for different Projects conflict; they do not receive independent records. A current owner can replay the same request after state changes; a revoked session cannot replay it.

## Operation inventory and remaining composition

Inspected against `packages/contracts/openapi/openapi.yaml` and the [coordinator command inventory](command-idempotency.md). This is an application/source mapping, not a claim that these HTTP routes are served.

Event stream and Evidence reader passed to application calls are trusted deployment dependencies. They must use the same authoritative Instance data as the coordinator. Event replay windows are deployment configuration, never client input. The Evidence reader retains its existing sequential-read consistency limits. Neither auth nor this boundary stores product state or changes Worker/Provider contracts.

## Committed Workflow selection

`attach.WorkflowReader` implements `ports.ProjectWorkflowSource`, reusing the Attacher's hardened, bounded Git process path and existing strict `workflowdef` parser. Trusted composition supplies the same Instance's Project clone store; the reader captures its persisted active root. It checks the root's current Project identity, refuses shallow clones, requires a full lowercase commit ID naming a commit, and checks its root commit against the current history using ADR-0046's smallest-root rule. Missing/foreign content returns bare `ErrNotFound`. Only a regular committed `.amaru/workflows/<id>.yaml` blob is read; symlinks, path selectors, mismatched IDs, invalid/oversized definitions and unknown format versions are refused. Repository/parser errors omit raw diagnostics and values. Working-tree edits are not loaded, repository content is not executed, and no Project file or operational record is written by loading.

`ProjectAccess.Workflow` checks live authentication and attached Project membership before calling the trusted source and again after source IO. `RunWorkflowRequest` carries only the command key, Workflow ID, explicit commit ID and variable overrides. `RunWorkflow` loads that definition and rechecks authentication in `Submit`, then reuses existing validation, Policy/Approval, snapshot pinning and atomic command outcomes. The explicit revision keeps retries stable after HEAD changes; changing it with an existing key conflicts. Loading makes no trust decision and grants no execution permission. Draft definitions can be queried but cannot run. No cache is introduced, so Projects and revisions share no mutable definition entry.

The requested Git object must remain available to load before replay. If it is removed, this application call fails closed; the existing Execution's persisted snapshot remains queryable. Product HTTP replay semantics still require composition acceptance.

The compact clone-location lookup uses the persisted binding described below, never a public path parameter. Execution clone provenance is recorded as described below; product composition still needs the HTTP contract mapping. This internal application request is not a new wire contract. Other definition types remain pending. Discovery settings now use the Platform store described below; the wider execution configuration format remains proposed. Neither slice introduces configuration-file syntax or changes `ResolveConfig` precedence. Public Environment selection also remains a separate gate.

## Project discovery settings

[ADR-0064](../architecture/adr/0064-project-discovery-settings-live-in-platform-state.md), approved in PR #338 and superseded with its settings semantics retained by [accepted ADR-0065](../architecture/adr/0065-tool-native-skill-discovery-remains-m7.md), is implemented at the domain/store/application layers for the existing `importClaudeSkills` switch. `ports.SettingsStore` is implemented by the existing fake and PostgreSQL Project stores. Settings belong to the attached Project identity within this Instance; clones of the same identity share the preference. An attached Project with no settings row reads false; a missing Project returns bare `ErrNotFound`. There is no repository importer, user-wide fallback or settings file write.

Trusted composition supplies the Instance's settings adapter to `ProjectAccess.Settings` / `UpdateSettings`, like the existing Evidence reader dependency. Every operation authenticates the current owner and checks attachment before accessing settings. The unversioned patch accepts an explicit boolean, including false, and repeated requests recheck authorization. Empty typed patches are invalid. `domain.ParseUpdateSettings` additionally rejects unknown fields, null, non-boolean and malformed JSON at the HTTP boundary; application callers use the typed patch. The settings HTTP adapter authorizes before decoding/access and uses this strict parser rather than permissive struct decoding.

PostgreSQL reads default false without inserting a preference. One upsert atomically writes the existing field and returns only after commit; concurrent first writes serialize, with the last committed explicit value retained. A failed statement rolls back. The fake serializes updates under its Project mutex. The additive migration creates `project_settings` with a Project foreign key, leaving identity, trust, configuration and prior records unchanged. No dependency or infrastructure is added. No settings-change Event, expected-version conflict or original-outcome replay is promised.

Enabling this preference grants no trust, Capability or execution authority: the settings path changes only its own boolean. Actual Skill discovery has not been wired to it. Committed execution configuration remains separate under ADR-0039. Contract descriptions and generated SDK now describe Platform storage; shared fixtures cover explicit false, null, string and unknown-field updates. The SDK fake-fetch test checks selected Project paths and false preservation, not a serving Platform API.

Shared fake/PostgreSQL conformance covers two Projects with matching names, defaults, independent updates, repeated patches, missing Projects, invalid/cancelled no-write paths, concurrent first writes and final-value reads after adapter recreation. PostgreSQL tests additionally exercise statement rollback and upgrading an existing database without inventing preferences. Application tests cover foreign/invalid Project refusal and rejected writes after session revocation or loss of owner role. See the [Linux settings record](../validation/m3/2026-11-12-linux-prj-002-settings.md).

Remaining M3 gates: startup wiring and full SDK product acceptance, including rejected/foreign writes leaving settings and trust unchanged. Actual discovery at two attached roots and unchanged content-trust requirements are M7 gates under ADR-0065. Multi-Organization authorization, actual PostgreSQL server restart/process kill and native macOS/Windows settings runs are not validated here. #191/#18/M3 remain open. The independent Worker shutdown cancellation defect [#339](https://github.com/rluders/amaru/issues/339) is fixed by merged PR #341, with merged-result Linux `make check` passing.


## Guarded settings HTTP adapter

`httpapi.SettingsHandler` implements the existing `GET` and `PATCH /v1/projects/{projectId}/settings` resource through `localauth.Auth.Handler` and `ProjectAccess`. Trusted composition supplies access bound to that same Auth and Instance stores. Clients percent-encode the complete Project key as one path segment; remote keys containing slashes and `#`, and local `id:` keys, are covered. No alternate identity or root-path lookup is introduced.

Both methods authenticate and perform an authorized settings read before responding or decoding a body. PATCH accepts JSON only, bounds the body to 4 KiB, uses `ParseUpdateSettings`, then rechecks current authorization in `UpdateSettings` before the atomic write. The preflight deliberately adds one read to PATCH so a missing/unattached Project is refused before body consumption, without a second public authorization API. A concurrent update does not use the preflight value: the authoritative store applies the explicit patch. Fixed error envelopes map invalid input to 400, authorization failure to 403, absent Project to 404 and unexpected store errors to 500, without raw diagnostics. Auth middleware supplies its existing 401/Host/Origin/CSRF rejection and protocol/security headers.

## Project-bound Artifact versions and content

`ProjectAccess.ArtifactVersions` authorizes the selected attached Project before index access, then checks every version's producing Execution against the coordinator's authoritative store. Only owned versions are returned, including when two Projects use the same Artifact ID. Missing, foreign-only and orphaned histories return bare `ErrNotFound` with no metadata. Existing immutable, globally assigned Artifact version numbers are preserved; filtering does not renumber versions or promise hidden numbering gaps.

`ArtifactContent` selects an exact owned version and opens its stored content hash through the trusted Instance BlobStore. Callers cannot use this operation to open a raw hash. Foreign or unknown versions never reach blob storage. Authorization is rechecked after index IO and after blob open; a revoked call receives no metadata or reader, and an already opened reader is closed. The authorized caller owns and closes a returned reader; continuous revocation of an ongoing stream is not implemented by this application operation. Storage errors return no partial result.

The fake-backed regression covers matching names, mixed histories, owned content, foreign/missing/orphaned versions, rejected credentials, revocation during both reads, dependency failures and unchanged history. This slice adds no storage mutation, migration, runtime dependency or new public contract. The inherited public Artifact schema describes Project-relative note paths; mapping it to versioned runtime Artifacts remains a reviewed contract/composition gate. These application methods are not serving HTTP endpoints. See the [Linux Artifact access record](../validation/m3/2026-11-12-linux-prj-002-artifacts.md). #191/#18/M3 remain open for the operation inventory's remaining gates.

## Exact-scope secret reference resolution

`coordinator.SecretResolver` implements the metadata lookup portion of accepted ADR-0062. Trusted Instance composition supplies the configured Organization, `ProjectAccess` and a `ports.SecretIndex`; request input supplies only the selected Project and an internal `domain.SecretReference`. There is no public reference schema or route in this slice. Authentication and attached Project membership are checked before lookup and again after index IO, including explicit Organization references.

A name-only or explicit Project reference checks exactly `(Organization, Project, name)`. An explicit Organization reference checks exactly `(Organization, name)`. Each resolution makes one index call; absent Project names never fall back to another Project, an Organization or a user name. Names remain case-sensitive and are not trimmed or aliased. Empty names, invalid UTF-8, NUL, unknown visibility and invalid Project selectors are refused without index access. Missing or inaccessible metadata returns bare `ErrNotFound`; backend failures return bare `ErrSecretUnavailable`, withholding raw diagnostics and any partial result.

The index reports existence only. Neither it nor this resolver accepts, decrypts, returns or delivers a value. A resolved `SecretIdentity` is a lookup key, never a permission, Grant or Approval. Policy and first-use Approval bound to the selected identity/Capability, an encrypted production backend, redaction and authorized assignment delivery remain **unimplemented in this slice**. There is no production index adapter or runtime composition yet. Existing configuration precedence, Workflow syntax, coordinator dispatch and Worker messages are unchanged. Fake metadata tests do not establish secret delivery or complete #191/#18. See the [Linux validation record](../validation/m3/2026-11-12-linux-prj-002-secret-resolution.md).

## Atomic local clone registration

**Implemented and locally tested (internal adapters only).** `ports.ProjectCloneStore` extends the existing Project-only store without changing its callers. `RegisterClone` creates a Project and selects its `domain.ProjectClone` in one transaction, or preserves the existing Project metadata and replaces only the active root. Store validation checks matching keys and nonempty, NUL-free roots; trusted attach owns native path validation and canonicalization. `ActiveClone` returns the selected root or `ErrNotFound` when no binding exists. The binding grants no trust or permission.

The fake serializes writes under its store lock. PostgreSQL locks the Project row until commit and stores the binding in `project_clones`, with unique Project/root constraints. Registration failures roll back both new Project and binding writes. A root currently selected by another Project returns `ErrExists`; it is not reassigned. Replacing a Project's active root releases the prior root's active ownership. Concurrent registrations of the same Project serialize through commit; request/response order does not select the root. Settings and other operational tables remain separate and unchanged.

`Attacher.Attach` now resolves the inspected root's symlinks to an absolute native path and calls atomic registration after its existing bounded read-only Git validation. Same-root repeats are idempotent; explicitly attaching a second clone sharing the same key selects it and preserves the original name/time/settings. Internal attach continues to accept relative paths for its existing callers; a future public attach handler must enforce the public absolute-root contract. Neither attach nor the store authenticates a caller: production composition must authorize before entry. No endpoint is added here.

Amaru is unreleased. Following the owner’s clarification on PR #349, `project_clones` is created in the initial `20261027120000_projects.sql` schema. There is no legacy upgrade, backfill or downgrade path for clone bindings. Existing development databases are outside this compatibility scope; this change does not reset or modify them automatically.

The [Linux validation record](../validation/m3/2026-11-12-linux-prj-002-clone-binding.md) covers both adapters, real temporary Git clones, PostgreSQL connection-pool reopen, collision/rollback, concurrent commit order, blocked-writer cancellation and fresh schema creation. Authorized persisted Workflow lookup and identity revalidation at use are implemented in the next section. Immutable Execution clone provenance, full process/server restart, public inspection/error mapping and HTTP/SDK composition remain follow-ups under #191/#18. A persisted root is neither proof that the directory still exists nor protection against concurrent filesystem replacement. No full clone-boundary, M3 completion or cross-platform runtime validation is claimed.

## Immutable Execution clone provenance

**Implemented at the internal application/store boundary:** the trusted Workflow source returns `ports.ProjectWorkflow`, containing both the parsed definition and the exact `ProjectClone` captured by that read. `ProjectAccess` checks the returned Project key and withholds both definition and provenance after authorization loss. `RunWorkflowRequest` still has no root field. It records the selected root as `DefinitionPin.CloneRoot` alongside the commit, content hash and canonical snapshot, in the same atomic Execution/Step/command-outcome write. Internal submissions without a Git source continue to support explicit definitions or Steps; they do not fabricate local provenance.

The fake store preserves the pin on Commit; the PostgreSQL immutable-pin trigger also protects the clone root from direct SQL updates. Reattachment affects new operations only. Clone selection is server-owned state and is excluded from the Submit intent fingerprint: the same authorized command/content replay returns its original Execution and root even after reattach, while a new key uses the newly captured root. The active clone must still supply the requested content before `RunWorkflow` reaches replay; it fails closed otherwise. Changing requested revision, definition, variables or attribution retains the existing conflict behavior.

Recovery reads the stored pin, snapshot and Step inputs, without resolving the current active clone or reloading Git. A missing original directory therefore does not prevent reading an already durable definition. This does not implement Provider filesystem access or recovery of inputs that were never persisted; future consumers needing the original source must validate that original location or fail/wait, never substitute the current active root. The local path is internal operational provenance, never a remote Worker instruction or a new public contract field.

Shared fake/PostgreSQL tests cover pin persistence, refused mutation, replay and new-key selection. The real temporary Git/PostgreSQL test reattaches another clone without the requested revision, deletes the original clone, closes/reopens the connection pool and reconstructs the coordinator, then reads the original durable definition and provenance. This is integration-tested on Linux, not a process/server restart or full product/Provider validation. [Validation record](../validation/m3/2026-11-13-linux-prj-002-execution-clone.md). The initial definition schema is updated directly under the pre-v1 no-legacy rule; existing development databases are not reset or upgraded.

### Read-only inspection adapter

`Attacher.Inspect` implements the first ADR-0067 slice: an absolute directory is inspected with the existing hardened Git process adapter, returning canonical repository root, identity, suggested name and committed config presence. It needs neither a Project store nor a clock and performs no registration or clone lookup. `Attacher.Attach` reuses that result before its existing atomic registration; stored metadata is still preserved on reattach. Internal Attach retains relative-path normalization; Inspect rejects relative roots.

Config presence means a regular committed `.amaru/config.yaml` blob, including an empty file; absent config is false. Symlinks, trees, malformed YAML, extra YAML documents and oversized output fail instead of pretending absence. Config mode and bytes are read using the same captured commit object, and dirty working-tree config is ignored. Git stdout over 1 MiB is rejected after draining/waiting, rather than parsing a truncated prefix. Parsing still reads only the existing identity/name subset, not the full future Project config grammar.

Linux integration tests use real temporary Git repositories, fake binding storage, and the race detector. They cover no repository writes, operation without storage/clock, root validation, config variants and unchanged selection/metadata after failed inspection. Existing attach/Workflow consumers run through the same suite. This adapter grants no authorization, exposes no HTTP resource and does not implement list/detail binding revalidation or public error redaction. Those later slices are described below; full product acceptance remains under #191/#18. Filesystem replacement races, native non-Linux behavior and full product validation are not established.

### Authorized Project application operations

**Implemented at the internal application boundary:** `ProjectAccess.AttachProject`, `Project` and `Projects` use the same compact human administrator check as existing Project operations. `ports.ProjectInspector` carries the existing native Git inspection result across that boundary; the coordinator imports no attach adapter, native path or process package. Native root checks remain in attach. There is no new dependency, storage schema or public wire type.

Attach checks authority before inspection, after inspection, immediately before atomic `RegisterClone`, and before returning. It uses the authoritative Project store already bound to `ProjectAccess`, preserves stored metadata, and maps foreign root ownership to conflict. Inspection failure prevents registration. A committed registration remains committed if the final authority check fails; a subsequent authorized retry can explicitly select the clone again. Live authorization and the store commit are separate operations, not an atomic revocation guarantee.

Detail/list read each Project's persisted binding once, inspect that captured root, and require both the Project identity and canonical root to match. A reattach during inspection affects later operations, without another binding lookup or substitution in the current result. Unknown/malformed IDs are not found. Missing bindings, invalid repositories/config and identity/root mismatches are conflicts. Other store/process failures propagate for the future handler's internal-error mapping. Lists return all inspected Projects sorted by stored name then key, or no results; reads never register or select clones. Authority and cancellation are checked after blocking store/inspection work and before returning results.
