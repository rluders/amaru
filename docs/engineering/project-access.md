# Compact Project access boundary

[ADR-0062](../architecture/adr/0062-project-bound-public-operations-and-secret-resolution.md) is accepted following owner approval in [PR #330](https://github.com/rluders/amaru/pull/330). `coordinator.ProjectAccess` implements the first #191 application slice around existing Execution operations. It does not implement a product HTTP server or complete [#191](https://github.com/rluders/amaru/issues/191).

Construct `NewProjectAccess` with the existing coordinator, the Instance's attached Project store and `localauth.Auth.Principal`. Every call rechecks authentication and attached Project identity. Compact composition has one configured Organization; its local administrator has owner access to those Projects. No membership database or multi-Organization authorization is implemented. The authentication callback is a trusted composition dependency, never a principal decoded from a request body or headers. A custom callback must enforce current authorization on every call.

`Auth.Principal` accepts only context established by that Auth instance's guarded downstream dispatch. Credential-free health/root requests and another Instance's context confer no identity. It refuses cancelled requests, logged-out/expired browser sessions and shutdown native contexts. Identity is the Instance-local `local-administrator`; session IDs and bearer values never become domain actor IDs. Origin/CSRF checks still precede authenticated dispatch.

`ProjectAccess` uses the coordinator's own authoritative store, preserving the trusted internal APIs for scheduling and recovery. It refuses invalid/unattached Project selectors before resource lookup. A foreign or missing Execution/Approval returns exactly `domain.ErrNotFound` with no returned child records, replay outcome or cursor. Approval ownership checks both its Project and its gating Execution. Ownership is checked before calling command replay or Evidence's context/artifact/audit readers. Existing stores already preserve immutable Execution Project identity; this slice changes no persisted storage contract, migration or transaction semantics. A read-only `ports.EvidenceReader` keeps the coordinator dependent only on domain/ports; trusted composition supplies the existing Evidence reader.

Manual Submit derives Project, principal and trigger from the trusted boundary. Cancel derives the human Actor and ActorID; Approval decisions derive their principal. Existing coordinator Policy, Approval, version checks, atomic writes and `(command name, key)` command namespace remain in force. Same-key requests for different Projects conflict; they do not receive independent records. A current owner can replay the same request after state changes; a revoked session cannot replay it.

## Operation inventory and remaining composition

Inspected against `packages/contracts/openapi/amaru.yaml` and the [coordinator command inventory](command-idempotency.md). This is an application/source mapping, not a claim that these HTTP routes are served.

| Public operation family | This slice | Remaining delivery gate |
|---|---|---|
| Execution create; Workflow run | Authorized manual `Submit`; `RunWorkflow` loads a named committed Workflow through `ports.ProjectWorkflowSource`, then binds Project/actor before replay | Agent/Skill/Environment resolution and wire-to-domain mapping; do not pass client definitions directly into the internal Submit request |
| Execution detail/cancel | Project-bound `Execution` and `Cancel` | HTTP handlers and shared contract/SDK acceptance |
| Execution definition/Evidence | Ownership before pinned definition return or Evidence assembly | Public mapping; direct Artifact ID/content access still needs its own ownership boundary |
| Project and Execution Event replay | Project authorization plus ownership of any Execution filter before the existing journal read; trusted clock/window | Typed envelope mapping, WebSocket lifecycle and cursor wire mapping |
| Approval detail/decision | Project-bound `Approval` and `DecideApproval` before replay | List/query adapters, HTTP handlers and contract/SDK acceptance |
| Project list/detail/attach | Existing Project/attach components are unchanged | Authenticated product composition |
| Execution lists, Work Packages/Items and dependencies | No new implementation | Project-selected authoritative query/mutation paths; reject cross-Project dependencies |
| Workflow/Agent/Team CRUD/source | `Workflow` reads the selected Project's committed Workflow at an explicit revision | Other definition types, CRUD, versioned API/disk reconciliation (#219) |
| Project settings | Authorized `Settings` / `UpdateSettings` and Platform persistence (ADR-0064) | Guarded settings HTTP adapter (below); settings SDK fixture composition below; full product composition and actual Skill discovery remain pending |
| Artifact list/detail/content; delivery-loop query | No new implementation | Project-bound access; delivery-loop implementation remains M4 |
| Health/auth, Provider/Capability discovery | Existing auth subset remains; identity now available to composition | Product startup, authenticated discovery and applicable protocol mapping |
| Grant and trust mutations (internal command inventory) | Existing trusted commands unchanged | Any future public exposure must authorize the target Project/Grant before replay; never expose raw coordinator methods |

Event stream and Evidence reader passed to application calls are trusted deployment dependencies. They must use the same authoritative Instance data as the coordinator. Event replay windows are deployment configuration, never client input. The Evidence reader retains its existing sequential-read consistency limits. Neither auth nor this boundary stores product state or changes Worker/Provider contracts.

## Committed Workflow selection

`attach.WorkflowReader` implements `ports.ProjectWorkflowSource`, reusing the Attacher's hardened, bounded Git process path and existing strict `workflowdef` parser. Trusted composition supplies an absolute attached-root lookup keyed by Project and the same Instance's Project store. It checks the root's current Project identity, refuses shallow clones, requires a full lowercase commit ID naming a commit, and checks its root commit against the current history using ADR-0046's smallest-root rule. Missing/foreign content returns bare `ErrNotFound`. Only a regular committed `.amaru/workflows/<id>.yaml` blob is read; symlinks, path selectors, mismatched IDs, invalid/oversized definitions and unknown format versions are refused. Repository/parser errors omit raw diagnostics and values. Working-tree edits are not loaded, repository content is not executed, and no Project file or operational record is written by loading.

`ProjectAccess.Workflow` checks live authentication and attached Project membership before calling the trusted source. `RunWorkflowRequest` carries only the command key, Workflow ID, explicit commit ID and variable overrides. `RunWorkflow` loads that definition and rechecks authentication in `Submit`, then reuses existing validation, Policy/Approval, snapshot pinning and atomic command outcomes. The explicit revision keeps retries stable after HEAD changes; changing it with an existing key conflicts. Loading makes no trust decision and grants no execution permission. Draft definitions can be queried but cannot run. No cache is introduced, so Projects and revisions share no mutable definition entry.

The requested Git object must remain available to load before replay. If it is removed, this application call fails closed; the existing Execution's persisted snapshot remains queryable. Product HTTP replay semantics still require composition acceptance.

The compact clone-location lookup is an injected trusted dependency, not a new persisted clone registry or public path parameter. Product composition still needs that registry and the HTTP contract mapping; this internal application request is not a new wire contract. Other definition types remain pending. Discovery settings now use the Platform store described below; the wider execution configuration format remains proposed. Neither slice introduces configuration-file syntax or changes `ResolveConfig` precedence. Public Environment selection also remains a separate gate.

## Project discovery settings

[Accepted ADR-0064](../architecture/adr/0064-project-discovery-settings-live-in-platform-state.md), approved in PR #338, is implemented at the domain/store/application layers for the existing `importClaudeSkills` switch. `ports.SettingsStore` is implemented by the existing fake and PostgreSQL Project stores. Settings belong to the attached Project identity within this Instance; clones of the same identity share the preference. An attached Project with no settings row reads false; a missing Project returns bare `ErrNotFound`. There is no repository importer, user-wide fallback or settings file write.

Trusted composition supplies the Instance's settings adapter to `ProjectAccess.Settings` / `UpdateSettings`, like the existing Evidence reader dependency. Every operation authenticates the current owner and checks attachment before accessing settings. The unversioned patch accepts an explicit boolean, including false, and repeated requests recheck authorization. Empty typed patches are invalid. `domain.ParseUpdateSettings` additionally rejects unknown fields, null, non-boolean and malformed JSON at the HTTP boundary; application callers use the typed patch. The settings HTTP adapter authorizes before decoding/access and uses this strict parser rather than permissive struct decoding.

PostgreSQL reads default false without inserting a preference. One upsert atomically writes the existing field and returns only after commit; concurrent first writes serialize, with the last committed explicit value retained. A failed statement rolls back. The fake serializes updates under its Project mutex. The additive migration creates `project_settings` with a Project foreign key, leaving identity, trust, configuration and prior records unchanged. No dependency or infrastructure is added. No settings-change Event, expected-version conflict or original-outcome replay is promised.

Enabling this preference grants no trust, Capability or execution authority: the settings path changes only its own boolean. Actual Skill discovery has not been wired to it. Committed execution configuration remains separate under ADR-0039. Contract descriptions and generated SDK now describe Platform storage; shared fixtures cover explicit false, null, string and unknown-field updates. The SDK fake-fetch test checks selected Project paths and false preservation, not a serving Platform API.

Shared fake/PostgreSQL conformance covers two Projects with matching names, defaults, independent updates, repeated patches, missing Projects, invalid/cancelled no-write paths, concurrent first writes and final-value reads after adapter recreation. PostgreSQL tests additionally exercise statement rollback and upgrading an existing database without inventing preferences. Application tests cover foreign/invalid Project refusal and rejected writes after session revocation or loss of owner role. See the [Linux settings record](../validation/m3/2026-11-12-linux-prj-002-settings.md).

Remaining gates: startup wiring, full SDK product acceptance and actual discovery at two attached roots with unchanged content-trust requirements. Multi-Organization authorization, actual PostgreSQL server restart/process kill and native macOS/Windows settings runs are not validated here. #191/#18/M3 remain open. The independent Worker shutdown cancellation defect [#339](https://github.com/rluders/amaru/issues/339) is fixed by merged PR #341, with merged-result Linux `make check` passing.


## Guarded settings HTTP adapter

`httpapi.SettingsHandler` implements the existing `GET` and `PATCH /v1/projects/{projectId}/settings` resource through `localauth.Auth.Handler` and `ProjectAccess`. Trusted composition supplies access bound to that same Auth and Instance stores. Clients percent-encode the complete Project key as one path segment; remote keys containing slashes and `#`, and local `id:` keys, are covered. No alternate identity or root-path lookup is introduced.

Both methods authenticate and perform an authorized settings read before responding or decoding a body. PATCH accepts JSON only, bounds the body to 4 KiB, uses `ParseUpdateSettings`, then rechecks current authorization in `UpdateSettings` before the atomic write. The preflight deliberately adds one read to PATCH so a missing/unattached Project is refused before body consumption, without a second public authorization API. A concurrent update does not use the preflight value: the authoritative store applies the explicit patch. Fixed error envelopes map invalid input to 400, authorization failure to 403, absent Project to 404 and unexpected store errors to 500, without raw diagnostics. Auth middleware supplies its existing 401/Host/Origin/CSRF rejection and protocol/security headers.

Tests cover two fake-attached Projects with matching names; native and browser clients, false/default/repeated updates, encoded selectors, no dispatch/body reads for rejected auth or Project access, logout, revocation during body IO, malformed/oversized/failed body reads, redacted store failure, the six shared patch fixtures and the owned resource's OpenAPI route inventory. Two native HTTP clients also exercise an actual loopback listener. These Go tests establish HTTP integration with fake storage; the SDK fixture evidence is recorded below. Product startup, actual browser execution, PostgreSQL HTTP integration or Skill discovery. The full contract's other routes remain unserved. See the [Linux settings HTTP record](../validation/m3/2026-11-12-linux-prj-002-settings-http.md). #191/#18/M3 remain open.

The fixture composes the same Auth instance, ProjectAccess and fake Project settings store with the real settings HTTP handler; health retains its existing auth guard. Missing Project reads/updates, anonymous reads, SDK refusal of mutations without CSRF, server rejection of wrong CSRF and post-logout reads/updates are checked; rejected operations leave settings unchanged.

The [Linux SDK record](../validation/m3/2026-11-12-linux-prj-002-settings-sdk.md) distinguishes this integration evidence from product startup, actual browser execution, real Git attachment, PostgreSQL HTTP/restart and full-resource SDK acceptance. No discovery runs, trust grants, configuration syntax, dependency or infrastructure is introduced. #191/#18 remain open for the inventory's other gates.

## Discovery scheduling decision pending

After merged PR #343, review found a scope conflict: FEAT-SKL-003 schedules tool-native Skill import for M7, while accepted ADR-0064 requires actual discovery before full #191 acceptance. [Proposed ADR-0065](../architecture/adr/0065-tool-native-skill-discovery-remains-m7.md) recommends retaining the implemented settings resource and deferring discovery/import to M7. **This is not accepted:** the discovery gate above remains binding. Setting the boolean currently discovers nothing and grants no trust. No scanner, importer or new file grammar is implemented by the proposal; all other #191/#18 gates remain open.
