## Acceptance
| Criterion | Evidence level | What shows it |
|---|---|---|
| The same inputs produce byte-identical context | unit-tested and integration-tested | `TestAssembleContextGolden` compares the document with `domain/testdata/context.golden`; `TestAssembleContextIsByteIdentical` builds it 200 times; `TestAssembleContextNormalizesLineEndings` shows CRLF and trailing blank lines do not change it; `ContextSuite` builds the context of two different Steps from the same Skills, intent and Knowledge and gets the same bytes and hash, on the fake and PostgreSQL stores. Order is part of the input and is tested to matter. |
| The context is stored as Evidence | integration-tested | `ContextSuite` and `ContextStore` conformance: the document, hash, format and item list (kind, name, version, hash, bytes) are recorded per Step, read back whole, and never change (same inputs return the record, other inputs return `ErrConflict`). PostgreSQL refuses update and delete by trigger and checks the hash against the document. |

Also covered: a body that looks like a header cannot forge one (declared lengths); a Skill whose body is not the content its hash names, a duplicate Skill or Knowledge path, a Knowledge path outside the Project, text that is not UTF-8 or holds a NUL and a document over 4 MiB are refused; a Skill that has become untrusted keeps the context from being built; a Step that already started or was refused, an unknown Step and a missing store are refused.

Evidence level: unit-tested (pure function, golden) and integration-tested on Linux (fakes, plus PostgreSQL for the store). No real Agent or Provider was given a context.
