# Ordered Event stream core

FEAT-EXE-004 ([#135](https://github.com/rluders/amaru/issues/135)) is implemented and unit/integration-tested on Linux as an internal replay core over committed Execution Events. This is fresh Amaru code under the owner's 2026-10-28 issue decision. No prototype eventbus was migrated. Public WebSocket transport and API envelope composition remain under [WP-M3-06](../architecture/WORK_PACKAGES.md#wp-m3-06-public-api-events-and-local-authentication); this core does not serve clients yet.

`ports.EventStream.ReadEvents` takes an authorized Project ID, an optional Execution ID, a nonnegative Project cursor and a page limit of 1–1000. The trusted Platform caller supplies its clock and deployment replay window: `domain.CompactReplayWindow` is 7 days; `domain.ServerReplayWindow` is 30 days for server and Cloud. These are the deployment defaults, not Worker timestamps or client-selectable query parameters. Deployment configuration/API wiring is not implemented here.

`ExecutionStore.Commit` appends the Project journal index in the same PostgreSQL transaction as the state transition and existing per-Execution log. Each returned `StreamEvent` carries its Project `Seq` and original `ExecutionEvent.Seq`. Project cursor assignment locks a transactional counter through commit, so concurrent Executions cannot publish a later cursor ahead of an uncommitted earlier one. Rollback consumes no cursor and leaves no state or Event. The migration and checksum manifest are forward-only additions to the existing PostgreSQL store; no new infrastructure or dependencies are introduced.

A read uses one repeatable-read, read-only transaction for the Project high-water mark, replay floor and page. Records appear in Project cursor order, regardless of their occurrence timestamp. Cursor reads are exclusive (`seq > after`); repeating a read without a write returns the same identities. Consumers deduplicate by Project and sequence internally. API IDs, typed public envelopes, authorization and transport reconnect are separate composition work under #18/#219. This implementation indexes existing Execution Events; Work/Workflow/Agent change producers and the combined Grant/Approval/Policy audit stream are still #219/#188 work, not silently included.

A full page resumes from its last Event. A short or empty page advances to the snapshot's Project high-water mark, including when filtering by Execution. Execution filtering never reads another Project, and uses the Project cursor rather than confusing it with the per-Execution sequence. The service/API must enforce caller access to the Project before using this internal port; no authentication server or Cloud tenant isolation is claimed by this storage check.

Replay eligibility uses Platform recording time (`clock_timestamp()` at journal insertion), not `ExecutionEvent.At`. A cursor before the highest expired journal entry produces `ResyncRequired` with `type: resync_required`, `reason: cursor_too_old` and `resumeFrom` equal to the committed high-water mark. A cursor ahead yields `cursor_ahead`. There are no partial Events alongside a resync result. A cursor exactly at the expired boundary can read the retained suffix. This bounds the replay window logically; physical cleanup and broader evidence retention/redaction remain [ART-003](https://github.com/rluders/amaru/issues/125). This is not a physical-deletion guarantee.

On upgrade, historical per-Execution logs cannot establish the commit order across Executions. For each Project with existing Events the migration reserves cursor 1 as an unavailable-history baseline, preserves the original logs, and fabricates no journal entries. Reads before that baseline return `history_unavailable`; subsequent Events begin at cursor 2. Fresh Projects begin at cursor 1 with no gap. A restart retains counters and history in PostgreSQL. After any resync, reload authoritative state and then resume from `resumeFrom`; clients must reconcile replay by entity revision/idempotent application because a state read and stream read are not one client transaction.

The shared `porttest.EventStream` suite runs against the fake in `make check` and PostgreSQL with the `pg` tag. PostgreSQL cases additionally exercise uncommitted visibility, restart, journal failure rollback, retained suffixes and migration history. See the [Linux EXE-004 record](../validation/m3/2026-11-12-linux-exe-004.md) for exact commands, outcomes and limits.
