# Egress consent (POL-004)

Status: implemented and integration-tested for the explicit HTTP sender path. This is fresh Amaru code; no predecessor sender is migrated. The single Policy evaluator and Grant model remain those of [ADR-0037](../architecture/adr/0037-one-policy-evaluates-capabilities-grants-and-approvals.md).

`egress.Sender` checks consent before DNS, dialing or reading the request body. Its required `Authorize` callback is `Coordinator.EgressConsent(assignment)`, bound by the trusted composition root to one running Worker attempt and fencing token. The coordinator reads the stored Execution's requester, trigger, Project, pinned definition and current trust; callers cannot supply replacement authority. It refuses cancelled Executions, expired leases and stale attempts. Every request re-evaluates `net.egress` on the normalized URL resource against current Grants and deny rules. A Step-wide Approval does not consent to another URL: this path requires a covering Grant and refuses `require_approval`. Creating a URL Approval from a sender call is not implemented.

The coordinator commits an `egress.decision` Execution Event with the Step id, time and Policy decision before sending. A failed commit prevents the send. The event records authorization, not an HTTP delivery result or permission to reach a private address. It contains no URL, query, headers or request body. The existing Grant audit records attribute standing consent to its human author. Combining these logs into one replayable stream remains POL-003 / EXE-004 work.

## Composition and configuration

The trusted Platform composition root supplies an `egress.Guard` with `Allow: domain.EgressAllowlist{PrivateHosts: ...}` and the sender callback. Pass the resulting sender to both `remotejob.Client.HTTP` and `remotejob.DownloadOptions.Client`; their `HTTPDoer` interface accepts it directly. The shared tests exercise the existing Provider request path with this wiring. There is no production Provider or serving composition root yet; this is an available, tested adapter path, not enforcement over all networking. The low-level remotejob helpers retain their existing defaults when no sender is injected; those defaults do not imply consent and must not be used as the Platform egress path.

The allowlist defaults to empty. It names private-address exceptions, independently of URL consent: a matching host or `*.suffix` allows private and loopback addresses, but never metadata/link-local, multicast, unspecified or reserved addresses. A configured endpoint is not a Grant. Only trusted composition code supplies the allowlist; no user or Workflow configuration loader is introduced. Organization/Deployment configuration-file wiring remains unimplemented.

Consent keys reuse `ParseEgressTarget`: `scheme://host:port/path`, with an explicit port and query/fragment omitted. Endpoint consent consequently covers query variations. Existing Grant matching also permits an explicitly granted URL prefix ending in `*`; this change adds no broader consent semantics. The sender refuses URL credentials and Host overrides, and sends the normalized endpoint with its original query only on the wire. Credentials in headers remain the Provider's responsibility.

Every connection resolves and vets all answers, rejects a mixed public/private answer unless explicitly allowlisted, and dials the vetted IP literal. Redirects are returned without following them; a new URL needs a separate consented request. Environment proxies and connection reuse are disabled. Sender errors expose neither raw URLs nor transport details; response content is still untrusted and must not be logged as safe. `Guard.Client` alone supplies address checks, not consent.

## Evidence and limits

`egress` tests cover consent before DNS/body reads, wrong URL, public/private/loopback destinations, explicit allowlisting, mixed answers, metadata refusal, DNS rebinding between requests, vetted-IP dialing, redirects, Host overrides and sanitized transport errors. The coordinator's shared `EgressSuite` runs against fake and PostgreSQL stores with a real loopback HTTP server: missing/wrong consent, allowed use, revocation, stale lease/fence, cancellation, deny precedence, trust and event-store failure. Trust standing is faked in that suite; existing trust suites cover its persistence separately.

Authorization is a point-in-time decision before a network side effect. A crash after its Event may leave no delivery, and cancellation/revocation after authorization cannot recall bytes already being sent. This adds no HTTP retry, deduplication or exactly-once guarantee. A sender is bound to a trusted Worker attempt; no remote authentication API is introduced. Arbitrary child-process networking, agent confinement, webhooks, production Provider wiring and native macOS/Windows validation remain outside this path. See [validation](validation.md) for evidence levels and Linux-first M3 scope.
