## Scope and boundary review

Verdict: sound as the first two concrete resource owners under accepted [ADR-0068](../../architecture/adr/0068-platform-process-readiness-and-bounded-shutdown.md). `internal/platform.Storage` acquires its database/sql pool in Start, verifies connectivity and exposes it only after completion readiness. `Schema` runs the existing checksum-verified embedded migrations under the existing advisory lock and publishes completion only after Apply returns successfully. WaitReady may precede Start. One absolute startup deadline bounds both initializers and is released from healthy lifetime; composition must extend that same deadline to the remaining stages and implement an independent aggregate watchdog.

The single outer Lane owns signal/cancellation/reverse Stop. Cancelling Storage.Start does not close the pool: dependents join first, Schema joins Apply/lock release, then Storage.Stop closes its pool once. Constructors acquire nothing. Late/blocked cleanup observes its cleanup context, reports failure, and may continue after timeout; process exit remains necessary if a driver never returns. No external server is stopped. No migration file, contract, Policy/Approval, authoritative state rule, driver version or dependency is changed. The standard library connector allows fake SQL connections in default checks; production composition must supply the already-pinned pgx stdlib connector. There is no generic lifecycle framework or nested supervisor. A plain one-shot function without WaitReady would allow downstream startup before connectivity/migrations complete; closing the pool in Start's defer would break dependent cleanup after Lane cancels Start contexts.

## Failure investigation and remaining limits

The first injected driver-panic run failed the assumed physical-connection cleanup assertion; a driver QueryContext panic also stranded a migration's deferred sql.Conn.Close. Source inspection of Go 1.27 database/sql confirms that Ping/query connection release follows the driver call and may be bypassed by a panic. Lane cannot repair those driver internals. The cases remain tested in disposable subprocesses with a cancellation deadline and bounded Lane shutdown; they assert the panic actually occurred, no later stage started, failure was returned and diagnostic secret canaries were not emitted. No driver-panic graceful cleanup is claimed. The migration-panic case demonstrates why initializer contexts alone cannot replace the independent aggregate startup watchdog. The pool-close helper contains its own panic without formatting values. Returned driver/migration/Lane errors remain unsafe to print, even though the slog handoff drops their diagnostic payloads.

No product entrypoint, configured connector, aggregate watchdog, bundled PostgreSQL process owner/owner-death protection, messaging/outbox, recovery/Worker service composition, HTTP/admission/discovery or diagnostic consumer is included. There is no process/server restart or crash-cut-point evidence here; pool and owner recreation against a still-running server is not process restart. Native macOS/Windows, real Provider and full public HTTP/SDK product composition remain **not validated**. #18/#92/#170/#191 and M3 remain open. The complete ADR-0068 production failure matrix is still owed; no new human architectural decision is requested by this slice.
