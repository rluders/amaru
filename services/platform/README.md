# services/platform

Go module `github.com/rluders/amaru/services/platform`: the Platform core. Introduced by WP-M3-01 ([#13](https://github.com/rluders/amaru/issues/13)) under [ADR-0049](../../docs/architecture/adr/0049-adapt-the-prototype-domain-and-ports-into-services-platform.md), which moves selected code from the earlier internal implementation at baseline commit `c8a2f6e` ([ADR-0032](../../docs/architecture/adr/0032-migration-baseline-is-a-pinned-commit.md)). Provenance per file: [PROVENANCE.md](PROVENANCE.md).

| `internal/domain`, `internal/coordinator`, `internal/store/postgres` (Policy and Grants) | Capability policy and Grants (FEAT-POL-001, [#132](https://github.com/rluders/amaru/issues/132), [ADR-0055](../../docs/architecture/adr/0055-write-policy-grants-and-project-trust-in-amaru-with-the-prototype-as-reference.md)): `domain.Evaluate` is one pure function `(request, Grants, rules) → allow | require_approval | deny` with reason codes, in the ADR-0037 order (a deny rule wins; then an active Grant; then a require-approval rule; then an allow rule; else `policy.uncovered`). `domain.Grant` is scoped to the Organization or one Project, names a Subject (agent, workflow or plugin component) and exact Capabilities, may be limited to a resource pattern and bound to a definition hash (it stops matching when the definition changes), and records who made it and, if revoked, who and why. Only a human Owner or Admin makes or revokes one (`NewGrant`, `Revoke`); a Grant is never deleted or edited in place (the `grants` table has a trigger that refuses both). `domain.DefaultRules` allow the local Capabilities (`agent.run`, `check.run`, `git.commit`, `code.test`, `doc.convert`, `image.convert`, `media.transcode`) and deny the reserved `scm.pr.merge`; everything else, such as `mcp.call` and `asset.upload`, is uncovered and needs a Grant. `Coordinator.Submit` now requires `By` (the requester, with a human sponsor for an Agent, trigger or plugin) and records it with the Execution; it asks Policy for each Step and creates a Step Policy does not allow `refused`, with the reason code and an actionable message, before any Worker sees it. The lease path asks again, so a Grant revoked after `Submit` keeps a queued Step from starting (it waits with the reason and a `step.deferred` event) and a new Grant lets it start; an Execution with no recorded requester is never started. `Coordinator.CreateGrant` and `RevokeGrant` are the commands; `WithGrants` and `WithRules` configure them, and a Coordinator without a Grant store fails closed. `coordtest.PolicySuite` runs over both links against the fake in `make check` and PostgreSQL in `make platform-test-pg`; `porttest.GrantStore` runs against both stores. Consequential-action classification (FEAT-POL-002, [#187](https://github.com/rluders/amaru/issues/187)): `DefaultRules` also carry rule 12 and the ADR-0006 list. Without a Grant, `git.push`, `deploy.run`, `tracker.write`, `scm.pr.create`, `net.egress`, `plugin.install`, `plugin.upgrade`, `spend.paid` and `fs.delete` outside the worktree are `require_approval`, each rule with an `ActionClass` (`publish`, `deploy`, `external_write`, `egress`, `permission`, `spend`, `delete`) that the reason repeats; `fs.delete` inside the worktree is allowed and `scm.pr.merge` is denied. The decision is the same for every trigger (manual, webhook, schedule, delivery loop) and every principal kind; nothing below the Organization can lower a default (a Project rule cannot allow, a Workflow or plugin supplies no rules, and an allow rule does not beat a requirement), only an Owner's or Admin's Grant does. The Capability ids for these actions are proposed names that are not in the catalog yet. A `Step` carries no resource yet, so through `Submit` the resource-dependent `fs.delete` rules cannot apply and an `fs.delete` Step is uncovered; the classification is exercised through `domain.Evaluate` with a resource. Audit trail (FEAT-POL-003, [#188](https://github.com/rluders/amaru/issues/188)): every Grant change is an `AuditEvent` in one append-only, gapless, ordered log (`ports.AuditLog`, replayed with `Audit(after, limit)`), with the actor (the human's id, or `platform`), the reason, the target and the Project. The Grant store writes the event in the same transaction as the change (`domain.GrantAuditEvent` derives it), so a Grant cannot be made, revoked, lapsed or expired without an event, and a refused write leaves none. Kinds today: `grant.created`, `grant.revoked`, `grant.lapsed`, `grant.expired`. PostgreSQL assigns `seq` from a one-row counter locked by the writing transaction (`audit_counter`), and a trigger refuses any update or delete of `audit_events`. Not covered: Approval events (there is no Approval yet, FEAT-REV-001), Policy changes (rules come from `DefaultRules` and `WithRules` at construction; no command changes them while running, so there is nothing to record yet), and `grant.lapsed` and `grant.expired` are never produced because nothing records a lapse or an expiry yet. The log is separate from the per-Execution event log; merging them into the one ordered stream with replay is FEAT-EXE-004 ([#135](https://github.com/rluders/amaru/issues/135), still open). There is no API to read the log. `porttest.AuditTrail` runs against both stores, `coordtest.PolicySuite` through the coordinator, and PostgreSQL tests cover append-only and gapless numbers under concurrent writers. Durable Approval Step (FEAT-REV-001, [#195](https://github.com/rluders/amaru/issues/195)): when Policy answers `require_approval`, `Submit` creates the Step `awaiting_approval` and one requested `domain.Approval` (the `policy_required` gate) in the same write (`CreateOnce` takes the Approvals; table `approvals`), so a restart finds both and nothing runs while it waits. `Coordinator.DecideApproval` takes an idempotency key, the decider, the outcome, a rationale and the Evidence digest the person was shown; it records approver id and role, time and digest, and in the same write queues the Step (approved) or ends it `failed` with code `approval_rejected` (rejected, which needs a rationale). Only a human Maintainer, Admin or Owner decides; an Agent, trigger or plugin never does, whatever role it carries; a stale digest is `ErrEvidenceChanged`. At the lease path an approved Approval covers its own Step's `require_approval` (not a `deny`). Cancelling an Execution withdraws a waiting Step (`StepExecution.CancelAwaiting`) and voids its Approval. Requests, decisions and voids are audit events and `approval.approved` / `approval.rejected` Execution events. A decided or voided Approval is final (a database trigger refuses a change or delete). Evidence today: the Execution, the Step, a hash of its Capability and inputs, and the pinned definition. `coordtest.ApprovalSuite` runs over both links against the fake in `make check` and PostgreSQL in `make platform-test-pg`, including a restart before and after the decision; `porttest.ApprovalStore` runs against both stores. Not implemented: the Workflow `approval` step type and Work Item acceptance gates, a Workflow's reroute after rejection (a rejection ends the Step), expiry, Team requirements and separation of duties (FEAT-REV-007), re-requesting on changed Evidence and commit, diff and check-result Evidence (FEAT-REV-003), the inbox (FEAT-REV-002), an Event for a refused attempt, an API, and an Execution that finishes when its Steps all failed or were refused (it stays `queued`). Not implemented: egress allowlist and the private-destination deny (FEAT-POL-004), the first-use-of-a-secret requirement (needs Approvals, FEAT-REV-003), a record of each Policy evaluation (the audit log below holds Grant changes only; an evaluation's record is the Step `Reason` and `step.deferred`), rules from configuration scopes (rules come from `DefaultRules` and `WithRules` only), egress consent, Project trust, a Grant API, and the recording of a lapsed or expired Grant (they stop matching; the stored status stays `active`). |

The pin is immutable (`Commit` ignores it; a database trigger refuses an update) and `Coordinator.Definition` reads the Workflow back from the snapshot, never from a file or Git, so editing a Workflow changes no running or past Execution and a restart resumes with the pinned one. A step without a `capability` (agent, review, approval) is refused until those Steps can run. `coordtest.DefinitionSuite` runs against the fake in `make check` and PostgreSQL in `make platform-test-pg`. Variables (FEAT-WFL-003, [#211](https://github.com/rluders/amaru/issues/211)): `SubmitRequest.Variables` overrides the Workflow's declared variables, and `{{name}}` in step inputs is replaced before the Steps are created (`domain.Substitute`, one pass, so a value is never expanded again). An override for an undeclared name, a value over `MaxVarValue` (10000, at least `MaxIntent`, so a Work Item intent travels whole, F-15), a placeholder that names no variable or is not closed, and a result over `MaxResolvedValue` are refused, never cut. The pinned definition keeps the placeholders; the Steps hold the final values, and the overrides are part of the idempotency fingerprint. Step prompts are not substituted yet (no agent Step runs). Per-Step timeouts (FEAT-WFL-004, [#212](https://github.com/rluders/amaru/issues/212)): every Step has a wall-clock timeout, the default for its kind (`domain.DefaultTimeouts`: agent 60 min, tool and check 30 min) or its `TimeoutSeconds` override (Workflow step `timeoutSeconds` or `StepSpec.TimeoutSeconds`, stored on the Step), at most the Organization maximum (8 h; `WithTimeouts`); a larger or negative override is refused at `Submit`. The Assignment carries `Deadline` (lease time plus the timeout). The embedded Worker ends the Runner's context at the Deadline and reports a failed Result with code `timeout`; the Platform ends the Step `timed_out` (ADR-0044) with error code `timeout`, event `step.timed_out`, and never re-runs it, even when idempotent: a person resumes or cancels it. The Runner must stop what it started; killing a process tree is the OS layer's job and no OS layer exists yet. `coordtest.TimeoutSuite` runs against the fake in `make check` and PostgreSQL in `make platform-test-pg`. The Platform does not itself expire a running Step whose Worker went silent (that is Lease expiry, below). Remote jobs (FEAT-CAP-004, [#130](https://github.com/rluders/amaru/issues/130)): a Provider records the job it started with `embedded.ReportRemoteJob` (a `StepEvents` message with a `remote_job` event: id and `resumable`), which the Platform stores on the running Step (fenced like a Result; a malformed or stale event is dropped or revokes the attempt, and recording the same job again writes nothing). `Assignment.RemoteJob` (new field 12 of `worker.proto`, additive) carries the job on the next Lease. After a restart, `Reconcile` applies ADR-0042 rule 2: a running Step with a resumable job is queued again with its job and the Provider re-attaches instead of submitting; one whose job is not resumable ends `interrupted` and is never submitted again. `coordtest.RemoteJobSuite` runs against the fake in `make check` and PostgreSQL in `make platform-test-pg`; `embedded` tests restart the Platform around a fake remote service that keeps its jobs. Only `remote_job` events are acted on; other `StepEvents` types are accepted and dropped until the event stream exists. Cancellation (FEAT-EXE-003, [#152](https://github.com/rluders/amaru/issues/152)): `Coordinator.Cancel` takes an idempotency key and an actor (a human, or a Policy rule that names itself). In one write it ends every Step nobody holds (queued, interrupted, timed out) and records `execution.cancel_requested`; for each Step a Worker holds it sends the Worker a `Cancel` message (the `Cancel` message of `worker.proto`; `ports.Cancel`). The Worker ends the Step's process tree and reports `OutcomeCancelled`, and the Execution becomes `cancelled` when its last Step has ended; with nothing held it is cancelled at once. A repeat of the key returns the recorded outcome and signals nothing. After a restart `Reconcile` settles a cancel whose Worker is gone. `coordtest.CancelSuite` runs against the fake in `make check` and PostgreSQL in `make platform-test-pg`. Concurrency limits (FEAT-EXE-006, [#158](https://github.com/rluders/amaru/issues/158)): `Limits{Global, PerProject, PerEnvironment}` (default two per Project; zero means no cap; `WithLimits`) are checked before a Step is leased, so no Assignment is sent for a Step that would exceed one. Slots in use are counted from the Steps that are leased or running, so a restart cannot leak a slot. A Step held back stays `queued` with `Reason` `limit:global`, `limit:project` or `limit:environment`, and one `step.deferred` event records when it began to wait; a Project at its limit does not hold up another. `coordtest.LimitsSuite` runs against the fake in `make check` and PostgreSQL in `make platform-test-pg`. Every Step counts as a slot today (not only agent Steps), per-Project overrides do not exist, and one Platform process is assumed (the check is under a lock in the coordinator, not in the store). `SubmitRequest` now needs a `ProjectID`; `EnvironmentID` is optional and both are opaque ids. Not implemented: Lease expiry while running (timers), Step events, cancel, drain, secrets, process-tree termination for a Runner that does not use `osproc`, a Platform-side grace timer for a Worker that never reports a cancel, Platform-side expiry of a silent Worker, concurrency limits across Workers, Workflow graph and Execution completion, capability matching (a Worker that refuses must Offer again), remote Worker identity. |
| `internal/worker/embedded`, `internal/worker/inproc` | The embedded Worker (FEAT-ENV-001): it offers its free slots, accepts, heartbeats the Lease while a `Runner` works, reports the Result, and cancels running work when the link closes, without reporting (the restart rule decides). It imports only `internal/ports`, which `internal/arch` enforces, so it reaches the coordinator only through the Worker interface. `inproc.Pair` is the in-process transport. The Runner is an interface with test fakes only: no Provider, process execution or OS layer exists ([#78](https://github.com/rluders/amaru/issues/78), [#79](https://github.com/rluders/amaru/issues/79), [#152](https://github.com/rluders/amaru/issues/152)). |
| `internal/arch` | Architecture test: the core imports no OS, process, network, vendor or adapter package (negative-tested by adding a forbidden import). A second test keeps `internal/ports` and `internal/store/postgres` free of file-system imports, so nothing stored can land in a Project tree. |

**Wire shape:** the Agent contract carries `revision` and `hash` (the head's `AgentVersion`), and `UpdateAgent`/delete carry `expectedRevision`, which `AgentHistory` checks. Nothing serves the API yet.

Nothing else of the Platform exists yet: no API, Provider, process execution, timers, outbox or message bus, and no remote Worker or WebSocket transport. Approval states arrive with the other sub-issues of #13. Display-key allocation (the per-Instance counter) needs storage and arrives with WP-M3-02.

## Check
`make platform-test` (part of `make check`). Tests use no real agents, network or paid APIs.

## PostgreSQL tests
`make check` stays offline. Tests that need a server carry the build tag `pg` and read the DSN from `AMARU_TEST_PG` (a role that may create databases; each test migrates its own throwaway database):

```
AMARU_TEST_PG='postgres://user:pass@127.0.0.1:5432/postgres?sslmode=disable' make platform-test-pg
```

`make check` compiles them (`go vet -tags pg`) but does not run them. Linux only so far: they were run against PostgreSQL 17 on Linux, not on macOS or Windows.

## Migrations
Add a goose-format file `internal/store/migrations/sql/<YYYYMMDDHHMMSS>_<name>.sql` with an `-- +goose Up` section only (migrations are forward-only; a `Down` section is never run), then refresh the manifest with `go test ./internal/store/migrations -update`. Never edit a released file: goose keeps no file hash, so only `migrations.sum` (checked in `go test`) catches an edit made after release, not a live database. ADR-0051 replaces ADR-0023's `atlas.sum` with this manifest because the Platform does not link Atlas (see Dependencies).

## FEAT-PRJ-005 review against the data architecture
[DATA_ARCHITECTURE §1](../../docs/architecture/DATA_ARCHITECTURE.md#1-data-classes) classes, as applied to the Project record:
- **Project knowledge, Definitions** stay in the user's repository. The `projects` table holds none of it and the Platform writes nothing there.
- **Operational state** (clone records, Work, Executions, Approvals) is not in this table. It will be keyed by `projects.key`; none of it exists yet.
- **Secrets and credentials** never enter the key: `NormalizeRemote` drops the user-info part.
- **Not covered:** attach and detach flows (FEAT-PRJ-001, 006), the `.amaru/` reader, clone records, and linking two remotes as aliases (ADR-0046). The review is against the documents; no click-through exists.

Aliases that normalize differently (a renamed or transferred remote, a mirror on another host) still need an explicit user link (ADR-0046); linking is not implemented.
