## Acceptance evidence

[LimitsSuite](../../../services/platform/internal/coordinator/coordtest/limits.go) is shared by the fake and PostgreSQL Execution stores. Its existing cases verify the default two slots per Project, global limits across Projects, Environment limits across Projects, independent scopes, queued reasons, completion and rejection release, and zero-as-uncapped configuration. This change adds the serialized-link invocation and 15 focused lifecycle scenarios (five per scope), with all three limits configured and each scope taking its turn as the tightest constraint:

- Simultaneous offers from two Worker sessions cannot publish more than one assignment. Zero Worker credit publishes none. Remaining Steps are queued with the limiting scope's reason.
- Success, failure and cancellation each admit exactly one waiting Step. A cancellation request retains capacity until the Worker reports cancellation. Every result is repeated: the duplicate is acknowledged without new Events or another assignment, and one further Step remains queued with its reason.
- Startup reconciliation removes a lost running Lease and lets waiting work acquire the slot. Repeated reconciliation preserves Events and does not admit extra work. The old session is stopped before the fresh coordinator starts; these are instance restarts, not process-kill tests.

**Integration-tested with fakes:** both Worker links use the actual coordinator and fake store. **Integration-tested against PostgreSQL:** the same suite uses the real adapter and disposable database with fake Worker messages. The default limit and queued-reason criteria are covered within the current all-Step accounting model; none of these tests is real-provider or distributed-scheduler validation.

## Boundaries and limitations

No production code, dependencies, contracts, infrastructure or migration changes are needed. The existing Platform lock serializes counting, checking and Lease commits before assignment publication; slot usage is derived from authoritative store state, not a separately decremented counter. Worker sessions communicate through the existing ports. Existing architecture checks remain applicable.

Scope remains one coordinator process serving multiple Worker sessions. No distributed Platform scheduler, real remote Worker, real provider, native macOS/Windows run or client UI is validated. All leased/running Steps count today; agent-only accounting and per-Project overrides remain unimplemented, as identified in #158. Zero limit means uncapped; zero available capacity is exercised by an occupied slot and by zero Worker credit. Startup recovery here replaces coordinator instances; process-kill durability evidence remains separately scoped in [EXE-002](2026-11-12-linux-exe-002.md). Native macOS and Windows remain best effort for M3 under the [owner decision](../../engineering/validation.md#scope-decision-product-owner-2026-11-12).

Review and designated-base integration remain required before #158 closes. Parent #15 also needs #157 and integrated acceptance. No new human architecture decision is needed for this verification-only change.
