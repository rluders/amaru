## Acceptance
| Criterion | Evidence level | What shows it |
|---|---|---|
| Trust is content-bound | integration-tested | A Workflow trust holds the `sha256:` hash of the pinned definition; `TrustSuite` runs a trusted definition, then an edited one (refused `policy.trust_changed`), then trusts the edit (runs) and shows the old definition is no longer trusted. `TestStanding` covers the cases in the domain. The Project trust is bound to the Project key, which includes the root commit. |
| Changes to trusted content require re-trust | integration-tested | The same subtest; a revoked trust also stops a queued Step at the lease path until a human trusts again. |
| Untrusted Projects are read-only to Agents | integration-tested, **partly** | An untrusted Project is denied every request for every principal kind, and no Grant, Approval or allow rule lifts it (`TestUntrustedProjectIsClosedToEveryRequest`). There is no read-only Capability, so "read-only" is met by running nothing, not by allowing reads. |

Also covered: only a human Maintainer, Admin or Owner trusts or untrusts (Contributor, Viewer, Agent, trigger and plugin refused and nothing stored or audited); a Coordinator without a trust store trusts nothing; each grant and revoke is an audit event with the actor and reason; PostgreSQL refuses deleting a trust and storing a content trust with a malformed hash.

Evidence level: integration-tested on Linux (fakes, plus PostgreSQL for the store). No real Project, Skill or forge was involved.
