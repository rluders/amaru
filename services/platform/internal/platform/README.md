# Platform process resource owners

Owner: Platform (#18). These are concrete composition helpers under accepted [ADR-0068](../../../../docs/architecture/adr/0068-platform-process-readiness-and-bounded-shutdown.md), outside domain, Coordinator, ports and Worker execution logic.

`Storage` opens its own database/sql pool inside Start from a pgx stdlib connector, checks connectivity and publishes completion readiness. `Schema` runs the existing checksum-verified embedded migration runner under its existing advisory lock. Register each in its own stage of the single outer Lane, storage first. Constructors acquire no resources; create fresh owners for each process run. WaitReady may precede Start. Both initializers use the same absolute startup deadline supplied by composition; it bounds initialization, not healthy lifetime. Pass that same absolute deadline to `NewLifecycle`; its independent watchdog covers all stages, including initializers that ignore cancellation.

`Lifecycle.Run` constructs one Lane with the safe diagnostic handoff and a shared positive shutdown budget; callers supply concrete stages in registration order. Its atomic `Ready()` latch opens only on aggregate readiness before the startup deadline and closes on failed runner exit and before forwarded caller cancellation or Lane teardown. The startup timer stops after readiness, so it cannot cancel healthy lifetime. Expiry remains a returned failure even when Lane regards the resulting context cancellation as intentional. Caller deadline expiry is also failure; intentional cancellation succeeds only with successful cleanup. Each Lifecycle is single-use. The production entrypoint must classify returned errors without printing them and exit unsuccessfully on failure; this helper cannot kill abandoned goroutines or owned child processes. No signal handler or restart supervisor is added alongside Lane.

Dependents obtain the pool through `Storage.DB` after readiness. Start cancellation leaves the pool available through dependent joins. Reverse Stop joins schema/lock release and closes storage last. Storage Stop starts cleanup exactly once even when its cleanup context has already expired, waits only within that context, and returns failure if the budget is exhausted. Cleanup may continue after timeout if a driver ignores cancellation; the entrypoint must treat that as failure and exit, as ADR-0068 requires. Storage cleanup panics are contained without formatting their values. Raw driver, migration and Lane returned errors remain unsafe to print; use the existing safe lifecycle diagnostic boundary.

`Recovery` constructs the shared Coordinator from the acquired pool and runs the existing Reconcile once under the same startup deadline. Register it after Schema and messaging and before background/execution/public stages. Its completion latch withholds both readiness and `Coordinator(ctx)` on failure, panic or cancellation. Downstream owners use that same Coordinator; Stop joins reconciliation without retrying it, undoing commits or closing the pool. Coordinator options configure existing behavior; they are copied at construction and applied inside Start. This readiness gate does not add an in-process restoration path after critical failure.

This is **partial implementation**, exercised with actual Lane and fake SQL connections in default tests, and PostgreSQL in the separately tagged tests. It creates no production entrypoint, configured connector, bundled PostgreSQL child owner, messaging/outbox, Worker composition, public admission, HTTP/discovery, or diagnostic consumer. It never stops an external database server, undoes migrations or deletes existing data. No new dependency or public configuration flag is introduced.

Driver panics can strand database/sql connection ownership or block a migration's deferred sql.Conn.Close before Lane sees the panic. Subprocess tests demonstrate failure without downstream admission under cancellation and a bounded shutdown budget; they do not establish graceful cleanup of a broken driver. The Lifecycle watchdog now bounds these subprocess cases without a parent timeout; production composition still needs the failure exit and child ownership described by ADR-0068. The owner expects the pinned pgx connector, not arbitrary third-party drivers.

Validation is included in root `make check` through `platform-test`. From `services/platform`, focused checks are `go test -race -count=1 ./internal/platform` and, with `AMARU_TEST_PG` pointing to a disposable server whose role can create databases, `go test -race -count=1 -tags pg ./internal/platform`. These are resource/stage tests, not full product acceptance.
